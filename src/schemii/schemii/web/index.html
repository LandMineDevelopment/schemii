PostgreSQL 17 · stored generated columns

Calculated-column expressions

Enter only the expression body. Schemii wraps it in GENERATED ALWAYS AS (…) STORED when exporting SQL.

Supported building blocks

  • Other non-calculated columns from the same row, referenced by name.
  • Literals, parentheses, operators, casts, and CASE expressions.
  • Only PostgreSQL functions and operators marked IMMUTABLE.

Examples

quantity * unit_price
lower(email)
CASE WHEN quantity > 0 THEN subtotal / quantity END

Not allowed

  • The calculated column itself, another calculated column, another row, or another table.
  • Subqueries or non-immutable values such as now() and random().
  • Complete SQL statements, semicolons, or SQL comments.

Schemii can track sibling-column references while you design without a database. PostgreSQL validates function volatility, result type, and full expression semantics when the exported change is applied.

Populated table · physical column order

How populated tables are reordered

Schemii uses a server-managed PostgreSQL transaction to preserve rows while rebuilding the physical column order.

Your rows are preserved

Schemii locks the table, copies its rows to a temporary table inside the connected PostgreSQL database, rebuilds the columns in the selected order, and restores every row by column name.

Dependent objects are preserved automatically

Modeled constraints, indexes, foreign keys, triggers, and identity values are recreated before the result is verified. You do not need to remove or restore them manually.

The change is atomic

If a step or final verification fails, PostgreSQL rolls back the entire migration, including the row copy and dependent-object changes.

Large-table warningMore rows take longer to copy and restore, require more temporary PostgreSQL storage, and keep the table exclusively locked for longer. Other database operations may have to wait until the migration finishes.

Temporary row data remains in PostgreSQL and is never stored in the Schemii metadata database.

Empty table · physical column order

Why database reordering is optional

Schemii's saved app order and PostgreSQL's physical column order are independent.

Your app order is already saved

The column order shown on the canvas and in the inspector is stored in Schemii without changing PostgreSQL. Deselecting this option keeps that visual order and leaves the database's physical order alone.

Physical reordering is an extra option

Schemii selects it by default for an empty table because there are no rows to copy. The server verifies that the table is still empty immediately before applying the reviewed migration.

Dependent objects are preserved automatically

If selected, Schemii temporarily removes and recreates modeled constraints, indexes, foreign keys, triggers, and identity values in the same PostgreSQL transaction. You do not need to manage them manually.

No data-copy costAn empty-table reorder still takes an exclusive table lock and performs schema changes, but it does not stage or restore rows.
